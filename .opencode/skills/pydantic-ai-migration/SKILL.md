# Pydantic AI runtime migration

Read in order: [DEVELOPMENT_STATUS.md](../../../DEVELOPMENT_STATUS.md), [ADR-0003](../../../docs/adr/0003-pydantic-ai-runtime-migration.md), [migration 001](../../../docs/migrations/001_PYDANTIC_AI_RUNTIME.md), [quality-and-evidence](../../../docs/development/quality-and-evidence.md), [project-invariants](../../../docs/development/project-invariants.md) and the relevant current implementation/tests. For eval work also use [eval-harness](../eval-harness/SKILL.md). Capture starting branch/SHA, PAIM task ID, the exact responsibility qualified/replaced, the Stage-9 behavior tests that define the reference, and any existing framework version.

Design checklist per change: what custom responsibility is replaced/qualified; which Pydantic AI public API/extension point supplies the generic mechanism; which D&D invariants stay outside the framework; can all side effects still route through `ToolExecutor`; can forbidden tool batches be rejected before the first side effect; what retry/concurrency/thread and Ollama/provider behavior changes; which old code is superseded and when it will be removed; what test proves parity rather than framework internals; what literal evidence proves each hard criterion.

Tool bridge: `ToolRegistrySchema → framework tool definitions/toolset → thin invocation adapter → ToolExecutor.execute(...)`. Never move repository/domain writes into direct framework tool functions, and keep one cohesive application policy layer (`DndAgentPolicy` or equivalent) for Stage-9 safety semantics rather than scattering policy across hooks. Framework tool visibility is not authorization.

Qualification first: prove critical framework behavior with focused offline tests/spikes before a large refactor; if a blocker appears, stop expanding scope and document it. A PAIM task may legitimately end qualified, selective-custom required, blocked pending architecture decision, or migration rejection recommended; do not hide a failed gate with a large workaround. For wrappers/decorators relying on exact request/retry/deferred behavior, identify the pinned Pydantic AI version, inspect its public source/contract, use public extension points, and add an offline construction/contract test before any expensive live run. Do not assume a duck-typed wrapper is accepted where production performs concrete `isinstance` checks, and do not weaken production validation for test instrumentation.

Parity: drive both sides from one shared logical scenario; use independent equivalent mutable state; prove reference/candidate identity before the matrix; compare provider-neutral DTOs, not private framework internals; assert exact project error categories; assert semantic model request count, executor attempts and handler effects for negative paths; never infer zero executor attempts from zero handler calls and never call different failure mechanisms parity. A shared negative helper must fail closed and must not accept arbitrary exceptions.

Live and eval gates: run offline fixture/constructor preflight, wrapper/type contract tests, scorer tests and env-unset skip behavior before any opt-in real Ollama run; a skipped live test is not proof its fixture graph can be constructed, and real smoke must prove the actual project path (machine-local profile → production model factory → production runtime → real Ollama → project policy/ToolExecutor), not a bare `Agent`. Eval comparison follows the same ground-truth, identity, configuration, literal-counter, frozen-dataset, metric-contract and critical-blocker rules as [eval-harness](../eval-harness/SKILL.md), measuring semantic model requests at the real boundary and never inferring request count from tool execution count.

Correction escalation: after two or more correction passes for the same evidence/harness defect class, stop and use [correction-review](../correction-review/SKILL.md) to find the repeated pattern and update reusable guidance. Cleanup: do not keep the old runtime merely as a runtime fallback; remove superseded generic code in the planned cleanup task once parity is accepted and green, leaving the reference in Git/main.

Final report: starting SHA/branch, changed-file inventory, framework version/API used, reference invariants tested, acceptance→evidence map, gates with exact results, canonical vs focused vs live command identity, framework limitations, classification (acceptable/selective-custom/blocker), removed/deferred old code, commit/push result and upstream equality.
